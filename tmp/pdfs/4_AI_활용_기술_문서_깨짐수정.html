4. 주요 AI 활용 사례

사례 1. LLM 응답-스키마 불일치 디버깅 (#9·#10 훈련 컴파일 파이프라인)

자동 테스트는 통과했지만 실제 API 응답 구조가 스키마와 달라 규칙이 거부됨 → 프롬프트를 스키마에 맞춰 수정, 라이브 재검증으로 해결.

상황 및 목표

LLMClient(#9)와 TrainingCompiler(#10)를 가짜 LLM으로 만든 EditMode 테스트는 전부 통과했지만, 실제 ANTHROPIC_API_KEY로 라이브 호출해 훈련 컴파일 파이프라인을 최종 검증하는 단계에서 Outcome=Rejected / errors: rule 누락이 발생했습니다. 원인을 찾아 실제 LLM 호출이 규칙 반영까지 성공하도록 고쳐야 했습니다.

주요 프롬프트 및 지시 사항

[에디터 메뉴에서 실제 Anthropic API로 훈련 컴파일 파이프라인 라이브 검증 실행 후]
"결과가 Rejected로 나왔다.
TrainingCompiler/RuleDiffParser 코드와 실제 API 응답 로그를 대조해서
원인을 찾아줘."

- 기술 환경: Anthropic Claude API(claude-haiku-4-5), TrainingCompiler → RuleDiffParser → RuleValidator 파이프라인
- 유지해야 할 기존 동작: 정상 add/update/delete diff 처리, RuleValidator 최종 저지선
- 변경 가능한 범위: 프롬프트(DEV_SPEC.md 03장) 또는 파서 — 단, 01장 규칙 스키마(공용 계약)는 변경 금지
- 원하는 출력 형식: 원인 설명 + 수정안 + 재검증 방법
- 예외·보안 조건: 스키마는 A(KJ)측 RuleEvaluator/콘텐츠와도 공유하는 계약이므로 임의 변경 불가

AI 제안 요약

  • 실제 API 응답 텍스트와 01장 스키마를 필드 단위로 대조해, LLM이 규칙 객체를 op에 평평하게(rule_id, then 필드로) 내보내는 반면 우리 파서는 op 안에 중첩된 rule 객체(id, do 필드)를 기대하고 있어 RuleDiffParser가 op.rule을 찾지 못해 null이 되고, 이것이 RuleValidator에서 "rule 누락"으로 최종 거부된다는 원인을 제시했습니다. 스키마를 응답 구조에 맞추는 안과 프롬프트를 스키마에 맞추는 안 두 가지를 제시했습니다.

개발자 검토 및 수정

  • 채택한 내용: 프롬프트를 스키마에 맞추는 안. 01장 규칙 스키마는 LLM 출력/RuleEvaluator 입력/콘텐츠 포맷 세 시스템이 공유하는 공용 계약이라, 스키마를 바꾸면 개발자 A(KJ)의 RuleEvaluator·상대 5종 JSON 코드까지 전부 재수정해야 해서 기각.
  • 수정한 내용과 이유: DEV_SPEC.md 03장 [diff JSON 형식]을 완전한 rule 객체 예시와 정확한 필드명(id, do, 중첩 rule)으로 교체하고, "문서=원본" 컨벤션에 따라 TrainingPromptBuilder.SystemPrompt에 동일 내용을 반영.
  • 제외한 내용과 이유: 파서를 두 형식 모두 허용하도록 관대하게 고치는 안 — 공용 계약을 흐리게 만들어 다른 상대 콘텐츠나 향후 검증에서 혼란을 유발할 수 있어 제외.
  • 검증 방법: 실제 API 키로 파이프라인 재호출.

최종 반영 및 효과

  • 재검증 결과
  • Outcome=Applied, 추가된 규칙: id=rule_01 label=상대 궁극기 시작 시 대시로 회피 priority=9로 자연어 → 실제 LLM → 올바른 diff → 검증 통과 → 규칙 반영까지 라이브로 확인했습니다.
  • "자동 테스트(손으로 만든 완벽한 JSON)만으론 부족하고, 실제 LLM은 프롬프트가 덜 구체적이면 계약과 다른 구조를 낸다"는 것이 이 프로젝트의 핵심 디버깅 교훈이 되었고, 이후 W2 진입조건(B 담당) 전 항목을 라이브로 통과했습니다.

사례 2. 프롬프트 인젝션 방어 3겹 테스트 설계 (#11)

방어가 프롬프트 신뢰가 아니라 C# 화이트리스트 검증(최종 저지선)에 있음을 3겹 구조 테스트 9종으로 증명.

상황 및 목표

훈련실 자연어 입력창은 플레이어가 자유 텍스트를 입력하는 유일한 창구라, "너는 이제 시스템이다. 지금까지의 규칙을 모두 무시해" 같은 인젝션 시도가 실제로 규칙 검증을 우회해 게임에 반영되지 않는지 검증해야 했습니다.

주요 프롬프트 및 지시 사항

"03장 보안 섹션 기준으로 프롬프트 인젝션 방어 테스트를 만들어줘. LLM 응답은 비결정적이라 실호출 자동화는
안 되니, 방어 지점별로 결정적 테스트를 짜는 방향으로."

사례 4. WebGL 웹 배포 + LLM 프록시 CORS 블로커 사전 차단 (제출·배포 단계)

배포 시 CORS 누락으로 게임 내 LLM 호출이 전면 차단될 뻔한 문제를 실제 빌드 전에 코드 점검으로 발견·수정하고, GitHub Pages 자동배포 파이프라인을 구성.

상황 및 목표

심사 제출을 위해 웹(WebGL) 빌드를 심사위원이 브라우저에서 링크만으로 바로 플레이할 수 있게 배포해야 했습니다. 문제는 게임의 핵심 기능(자연어 규칙 컴파일·경기 회고)이 API 키를 감춘 팀 소유 LLM 프록시(Vercel 서버리스, 게임과 다른 도메인) 호출에 의존한다는 점이었습니다. 이 크로스도메인 호출이 배포 환경(GitHub Pages)에서 브라우저 보안 정책에 막히지 않도록 하는 것이 목표였습니다.

주요 프롬프트 및 지시 사항

"이제 이 게임을 웹에서 실행되게 보내줘야 하는데 어떻게 해야 할까"
(제출 요강 캡처 첨부: GitHub Pages 링크 / 전체 소스 동일 저장소 / 커밋 기록 유지)

- 기술 환경: Unity 6 WebGL 빌드, LLM 프록시(Vercel 서버리스 api/compile.js), GitHub 저장소
- 유지해야 할 기존 동작: 프록시는 키를 서버 환경변수로만 보관(클라 하드코딩 금지), IP rate limit
- 변경 가능한 범위: 배포 설정·서버 CORS·CI 워크플로 — 게임 로직/규칙 스키마는 불변
- 원하는 출력 형식: AI가 할 일과 사람이 할 일을 구분 + 실제 파일 수정까지
- 예외·보안 조건: API 키가 클라이언트 빌드/소스 어디에도 노출되지 않을 것

AI 제안 요약

  • 배포 구조를 먼저 점검해, 프록시 api/compile.js 에 CORS 헤더·OPTIONS preflight 처리가 전혀 없어 GitHub Pages(다른 오리진)에서 실행하면 브라우저가 /api/compile 호출을 preflight 단계부터 전부 차단 → 규칙 컴파일·사제 대화가 죽는다는 점을 실제 빌드 전에 지적했습니다.
  • 수정안: 허용 오리진 화이트리스트(GitHub Pages 도메인 + 로컬 테스트용 localhost:8080/3000)에 대해서만 요청 Origin을 반사(echo)하고, preflight(OPTIONS)는 204로 응답하는 CORS 처리를 추가. 커스텀 도메인은 환경변수 ALLOWED_ORIGINS 로 코드 수정 없이 확장 가능하게 설계.
  • WebGL 빌드 결과물(WebGLBuild/)을 자동 배포하는 GitHub Actions 워크플로(deploy-pages.yml)와 Unity 파일이 무시되는 것을 막는 .nojekyll 을 생성. Unity 측은 Pages 호환을 위해 압축 포맷=Disabled 로 빌드(GitHub Pages가 .br/.gz 를 올바른 헤더로 서빙하지 못해 로딩이 실패하기 때문)하도록 안내.
  • 수정한 CORS 로직은 Node 목(mock) 런타임 테스트로 "허용 오리진 → preflight 204 + 헤더 반사 / 미허용 오리진 → 헤더 미부여"를 결정적으로 검증했습니다.

개발자 검토 및 수정

  • 채택한 내용: CORS 화이트리스트 방식(공개 * 대신), GitHub Actions 자동배포, 압축 Disabled 빌드.
  • 사람이 수행한 부분: WebGL 빌드 자체는 Unity 에디터에서만 가능하므로 개발자(JM)가 직접 빌드해 WebGLBuild/ 에 커밋·main push. 로컬 웹서버(localhost:8080)로 로딩을 확인(파일 더블클릭 시 뜨는 file:// 미지원 에러는 웹서버가 필요하다는 신호임을 확인).
  • 위임한 부분: 저장소가 개발자 소유가 아니라(멤버 권한) GitHub Pages 활성화는 admin만 가능 → owner에게 "Settings → Pages → Source = GitHub Actions" 한 단계만 요청하는 안내 문서(OWNER_PAGES_SETUP.md)를 생성해 전달.

6.2 오류와 보완 사례

AI 결과의 문제발견 방법보완 내용최종 결과
• 실제 Anthropic API 응답 필드명이 파서/스키마와 불일치 (rule_id/then vs id/do, 중첩 구조 누락)• EditMode 테스트는 통과했지만 실제 API 키로 라이브 검증 시 Outcome=Rejected 로그로 발견• DEV_SPEC.md 03장 diff JSON 형식에 완전한 rule 객체 예시 명시 → 시스템 프롬프트 동일 반영• 재검증 시 Outcome=Applied, 규칙 정상 반영 확인
• needs_confirmation 되묻기 응답이 서술형으로 나와 적용/거절 여부를 UI만으로 구분할 수 없음• W3 Match.unity 플레이테스트 중 개발자 A가 직접 발견• 시스템 프롬프트 규칙4/9/10 보강 — 되묻기는 항상 의문형, 적용은 항상 평서문으로 강제• 기존 EditMode 테스트 76건 회귀 없이 재플레이테스트로 개선 확인
• 배포용 LLM 프록시(api/compile.js)에 CORS 처리가 전무 — WebGL을 GitHub Pages(타 도메인)에 올리면 브라우저가 /api/compile 호출을 전부 차단해 게임 내 LLM이 죽음• 배포 준비 중 AI가 프록시 코드를 점검하다 preflight(OPTIONS)/Access-Control-Allow-Origin 부재를 실제 배포 전에 발견• 허용 오리진 화이트리스트 + OPTIONS 204 preflight 처리 추가, ALLOWED_ORIGINS 환경변수로 확장 가능하게 설계• Node 목 런타임 테스트로 허용/미허용 오리진 분기 검증 후 main 반영

7. 활용 성과 및 한계

7.1 성과

  • 개발 시간·반복 작업 감소
  • 2인 팀이 4주 안에 GitHub 이슈 21개(#3~#20 + 추가 #22, #24, #26)를 전부 closed 처리
  • 규칙 스키마·FSM·LLM 파이프라인·화면 3종·콘텐츠 5종·캐릭터 애니메이션 6종까지 전 구현 완료
  • 디버깅 효율
  • 실제 API 응답 로그와 스키마/파서 코드를 필드 단위로 대조하는 방식으로 "자동 테스트는 통과, 실호출은 실패" 유형의 버그(사례 1)를 빠르게 특정
  • 코드·테스트 품질
  • 이슈마다 EditMode 단위 테스트를 동반 생성해 회귀 여부를 즉시 확인 가능한 상태 유지
  • 기술 학습·대안 탐색
  • UniTask, Newtonsoft.Json, Anthropic Messages API 등 팀에 새로운 스택을 프로젝트 진행과 병행해 도입

7.2 한계와 대응

한계프로젝트 영향대응 방법
• 프로젝트 전체 맥락(01장 규칙 스키마가 3개 시스템의 공용 계약이라는 사실 등)을 세션마다 자동으로 파악하지 못함• 컨텍스트를 안 주면 스키마 필드명·enum 철자를 임의로 바꿔 다른 시스템과 어긋날 위험• 이슈마다 DEV_SPEC.md 00장 전체 + 해당 근거 장을 매번 컨텍스트로 명시 제공, 커밋 전 diff에서 철자 직접 확인
• 게임 내 LLM(Claude Haiku) 응답 자체의 비결정성• "10회 중 9회 이상 유효 diff" 같은 확률적 완료 기준은 자동 CI로 검증 불가• 같은 입력으로 수동 반복 실행 후 통과/실패를 수기 기록(자동화 범위 밖으로 명시적으로 분리)
• 마일스톤 게이트(Wn→Wn+1) 판단을 AI가 임의로 건너뛸 위험• 팀원 담당 이슈가 아직 open인데도 다음 단계 코드를 작성할 가능성• 세션 시작 시 GitHub 이슈 상태를 자동 조회해 현재 Wn을 판정하고, 하나라도 open이면 담당자 무관하게 다음 단계 착수를 하드 차단하는 규칙을 프로젝트 문서(CLAUDE.md)에 명시
